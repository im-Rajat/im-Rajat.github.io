Section 03 // Under The Hood

Technical Deep Dive & Mechanics

Explore the SQL mechanics, lock variations, timestamp pitfalls, and architectural trade-offs of each strategy.

Pessimistic Locking Mechanics

Database-level blocking via Lock Manager

Types of Database Locks (Click to inspect):
SELECT ... FOR SHARE;

Read Lock: Multiple transactions can hold a Shared Lock on the same row simultaneously to read data, but no transaction can modify it (acquire an X-Lock) until all shared locks are released.

Pros

  • Guaranteed Safety: Zero chance of lost updates; enforced strictly by DB engine.
  • No Wasted Compute: You don't run heavy business logic only to get rejected at commit time.

Cons

  • Deadlocks: Tx1 locks Row A & waits for B; Tx2 locks B & waits for A. Both freeze!
  • Connection Exhaustion: Hanging queries tie up database connection pools.
  • Terrible for UI Flows: Never hold a DB lock while a user fills out a web form.

Optimistic Locking Mechanics

Application/ORM conflict detection at Write phase

Why Version Integers Beat Timestamps Critical Gotcha

Always prefer an incrementing integer (version = version + 1) or UUID over a timestamp (updated_at). Under high concurrency, two transactions can execute within the exact same millisecond (`12:00:00.004`), causing a timestamp check to falsely pass and silently overwrite data!

WHERE version = 5 WHERE updated_at = '12:00:00.004'

Pros

  • High Scalability: Zero threads blocked on reads; blazingly fast throughput.
  • Zero Deadlocks: No locks held across steps means deadlocks are impossible.
  • Stateless HTTP Ready: Send `version = 5` to a browser form and verify 10 mins later.

Cons

  • Retry Storms (Thundering Herd): If 100 users buy 1 ticket, 1 succeeds and 99 fail & retry, hammering the DB.
  • Code Complexity: Must catch `OptimisticLockException` and write retry/merge logic.

Optimistic Locking

Because contention is low and user interaction spans across stateless HTTP requests, holding database locks would exhaust your connection pool. Use a version column instead.

Implementation Pattern:

Section 05 // Ace The System Design Interview

The 3-Part Interview Framework + Quiz

When an interviewer asks: "Explain Optimistic vs. Pessimistic locking and when you would use each", use this structured 3-part framework to deliver a staff-level answer.

Part 1 // 30-Sec Pitch

Under-The-Hood Definition

"Both are concurrency control strategies used to prevent race conditions and lost updates when multiple transactions modify the same data.

Pessimistic locking assumes conflicts are likely, so it locks the record at the database level when reading it—using SELECT ... FOR UPDATE—forcing other transactions to wait until the lock is released.

Optimistic locking assumes conflicts are rare. It doesn't lock rows on read; instead, it uses a version column. When updating, it checks WHERE version = old_version. If another transaction modified the row in the meantime, 0 rows are updated, and the application catches the exception and retries or aborts."
Part 2 // Real-World Mapping

Contention & Duration Trade-Offs

"Choosing between them comes down to contention rate and transaction duration:

I use Optimistic Locking when reads vastly outnumber writes and conflicts are rare, or when human interaction is involved—like a Collaborative Wiki, CMS, or User Profile update. It scales much better because we aren't holding DB locks open.

I use Pessimistic Locking when contention is extremely high and retrying is expensive—like a Flash Sale inventory system where 1,000 users fight for the same SKU, or a Core Banking ledger transfer. Optimistic locking there would cause 999 transactions to fail and trigger retry storms."
Part 3 // Staff-Level Nuances Click to expand

Drop One of These Bonus Points

1. The Atomic Update Alternative

Sometimes you don't need application-level locking at all. A single atomic SQL statement acquires a brief implicit row lock inside the DB engine in one round-trip:

UPDATE Inventory SET quantity = quantity - 1 WHERE id = 99 AND quantity > 0;
2. HTTP ETag in REST APIs

Optimistic locking isn't just for databases! In REST APIs, we implement it using HTTP ETag and If-Match headers (returning 412 Precondition Failed on conflict).

3. SKIP LOCKED & NOWAIT

To avoid connection pool exhaustion in pessimistic locking, modern DBs support FOR UPDATE NOWAIT (fails immediately instead of hanging) or FOR UPDATE SKIP LOCKED (ideal for database-backed job queues).
