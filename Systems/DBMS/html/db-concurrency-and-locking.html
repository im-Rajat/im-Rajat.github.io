Database Concurrency & Locking

Curated by Rajat Kumar

The Problem: The Lost Update

Imagine an online ticketing system. There is exactly 1 ticket left for a concert. Alice and Bob both click "Buy Ticket" at the exact same millisecond. Without concurrency control, the database might let both users read that 1 ticket is available, process the payment, and assign the ticket to both, resulting in negative inventory (data corruption) or an overwritten record (a lost update).

Race Condition

When two or more threads/users access shared data and try to change it at the same time, the final outcome depends on the exact sequence in which execution happens. This is unacceptable for reliable systems.

Pessimistic Locking

"I don't trust anyone." Pessimistic locking assumes conflicts will happen frequently. When a user reads a record with the intent to update it, the database places a strict, physical lock on that row. Any other user trying to read or update that row must wait until the first user finishes their transaction.

Pros

  • Guarantees absolute data integrity.
  • Prevents transactions from having to be rolled back/retried in application logic.

Cons

  • Performance Bottleneck: Users are queued up waiting.
  • Deadlocks: Transaction A locks Row 1 and needs Row 2. Transaction B locks Row 2 and needs Row 1. Infinite wait.

How it's implemented (SQL)

Using SELECT ... FOR UPDATE in most relational databases (PostgreSQL, MySQL, Oracle).

BEGIN TRANSACTION; -- This locks the row. Others trying to -- run this exact query will block & wait. SELECT balance FROM accounts WHERE id = 1 FOR UPDATE; UPDATE accounts SET balance = 150 WHERE id = 1; COMMIT; -- Lock is released here

Optimistic Locking

"I trust people, but I will verify." Optimistic locking assumes conflicts are rare. It allows multiple users to read the data without locking it. Instead, it uses a version number or a timestamp. When a user attempts to save changes, the system checks if the version in the database matches the version they originally read. If it differs, the update is rejected (an exception is thrown), and the application must handle it (usually by asking the user to retry).

Pros

  • High Scalability: No locking overhead, database is fast.
  • No deadlocks possible on the database level.
  • Great for web apps with high read/low write ratios.

Cons

  • Complex application logic: Developer must write code to handle `OptimisticLockException` and retries.
  • Poor UX if conflicts are frequent (users constantly get "Your changes were overwritten, try again" errors).

How it's implemented (SQL)

Adding a `version` column. Handled via the WHERE clause.

-- Step 1: Read data (No lock applied) SELECT balance, version FROM accounts WHERE id = 1; -- Application sees: balance=100, version=1 -- Step 2: Attempt Update (increment version) UPDATE accounts SET balance = 150, version = version + 1 WHERE id = 1 AND version = 1; -- If Rows Affected == 0, it means someone -- else changed the version! Throw Exception.

Interview Cheat Sheet

Feature Pessimistic Locking Optimistic Locking
Philosophy Conflict is highly likely. Lock first. Conflict is rare. Verify before update.
Mechanism Database-level row locks (FOR UPDATE) Application/Query logic (Version or Timestamp)
Performance Slower. Connections wait in a queue. Deadlocks possible. Faster reads. High throughput. No DB-level deadlocks.
Best Use Case Financial transactions, inventory management (last item). High write environments. CMS, Web form edits, profiles. High read / Low write environments.
Exception Handling Minimal. DB handles the wait automatically. Required. App must handle OptimisticLockException (retry or inform user).
